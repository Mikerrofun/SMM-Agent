# Architecture — SMM Agent

## Назначение

SMM Agent — backend-сервис, который автоматически анализирует Telegram-каналы конкурентов, генерирует идеи для новых публикаций и помогает создавать готовые посты в стиле Натальи.

Telegram в данном проекте является интерфейсом взаимодействия с пользователем, а не основой приложения.

---

# Основная идея архитектуры

Проект построен как набор независимых модулей.

Каждый модуль отвечает только за одну задачу.

Модули ничего не знают друг о друге напрямую и взаимодействуют через сервисы.

Это позволяет:

- легко изменять отдельные части системы;
- тестировать модули независимо;
- постепенно расширять функциональность без переписывания проекта.

---

# Общий поток работы

Каждый вторник и четверг запускается процесс генерации идей.

```
Cron
    │
    ▼
Parser ──────────► Repositories        (сохранить новые посты конкурентов)
    │
    ▼
Service (оркестратор)
    │
    ├─► AI: генерация идей батчами        (стадия 1)
    │
    ├─► AI: embeddings + дедуп по вектору  (стадия 2, без LLM)
    │
    ▼
Repositories        (сохранить идеи + пометить посты обработанными)
    │
    ▼
Telegram Bot        (отправить идеи со статусом NEW)
```

### Что происходит

Подробная модель данных и жизненный цикл сущностей — в
[`DataArchitecture.md`](./DataArchitecture.md); векторная часть — в
[`Embeddings.md`](./Embeddings.md). Ниже — как модули гоняют данные между собой.

1. Cron запускает задачу по расписанию и создаёт `GenerationRun` (статус `RUNNING`).

2. Parser получает публикации конкурентов, вышедшие **после `finishedAt`
   последнего успешного прогона** (по активным каналам `isActive = true`).

3. Новые публикации сохраняются в `CompetitorPost` (`isProcessed = false`).
   На этом этапе AI ещё не используется.

4. **Стадия 1 — генерация идей батчами.** Service разбивает новые посты на
   чанки по 15–20 штук. Каждый чанк уходит в OpenAI **одним запросом**; стиль
   Натальи задаётся промптом напрямую, эталонные посты больше не используются.
   Это резко сокращает число запросов.

   Ответ приходит строго по JSON schema (structured output) — массив идей, где
   каждая идея явно ссылается на исходный пост через `competitorPostId` (id мы
   сами кладём в запрос, AI обязан вернуть его обратно).

5. **Стадия 2 — дедупликация по вектору (без LLM).** Для каждой идеи Service
   считает embedding (`title + thesis`) и через pgvector ищет ближайшие записи
   среди `Idea` и `NataliaPost`. Если similarity ≥ порога (~0.85) — идея
   помечается `DUPLICATE` и не показывается; иначе сохраняется как `NEW`, её
   embedding пишется в БД и участвует в проверке следующих идей прогона.

6. Идеи сохраняются через Repositories; исходный `CompetitorPost` помечается
   `isProcessed = true` и получает `ideaId`. `GenerationRun` обновляется
   (статистика, число запросов, статус `SUCCESS`/`FAILED`).

7. Telegram отправляет пользователю идеи со статусом `NEW` (заголовок, тезис,
   цель, кнопка «Сгенерировать пост»). Отправленная идея → `SENT`.

8. После выбора идеи (`SELECTED`) AI генерирует полноценный пост (идея +
   оригинальный пост конкурента + промпт со стилем).

9. Готовый пост сохраняется в `GeneratedPost` и отправляется пользователю.

# Ключевые решения по потоку данных

Эти решения зафиксированы и не должны потеряться при реализации:

- **Батчинг генерации.** Идеи генерируются чанками по 15–20 постов одним
  запросом. Стиль задаётся промптом напрямую, эталонные посты больше не 
  используются — это режет число запросов в разы. Ответ — массив идей с явной 
  привязкой к `competitorPostId` через JSON schema.

- **Двухстадийность.** Стадия 1 — генерация идей (LLM). Стадия 2 —
  дедупликация по вектору (pgvector, cosine similarity, БЕЗ обращения к LLM).

- **Embeddings.** Поле `embedding` есть у `Idea` (от `title + thesis`) и
  `NataliaPost` (от `mainIdea`). Считается отдельным вызовом OpenAI
  (`text-embedding-3-small`, 1536 dim) после генерации идеи.

- **Статусы `Idea`:** `NEW`, `SENT`, `SELECTED`, `REJECTED`, `DUPLICATE`.

- **Контроль стоимости.** `GenerationRun` хранит число запросов в OpenAI и
  статистику прогона, чтобы отслеживать расходы при батчинге.

- **Retention (гигиена диска, не контроль промпта).** CompetitorPost — 30 дней,
  невыбранные идеи — 14 дней, дубли — сразу, выбранные идеи + посты — 90 дней,
  последние 50 прогонов. Раздувание промпта решается не удалением, а векторным
  поиском top-K (детали — в `Embeddings.md`).

# Ответственность модулей

| Модуль | Ответственность |
|---------|-----------------|
| `cron` | Запуск процессов по расписанию |
| `parser` | Получение новых постов из Telegram |
| `repositories` | Работа с базой данных |
| `services` | Координация всех модулей |
| `ai` | Работа с OpenAI |
| `bot` | Общение с пользователем через Telegram |
| `db` | Подключение к базе данных |
| `prompts` | Хранение AI-промптов |
| `core` | Общая инфраструктура проекта |
| `shared` | Общие утилиты и типы |

Второй источник контента — транскрипции встреч с клиентами. Он живёт по тем же
правилам: `shared/utils/pdfParser.ts` извлекает текст из PDF, `ai/transcriptPostGenerator.ts`
пишет пост, `services/transcript/` координирует попытки и дедупликацию,
`repositories/clientTranscriptRepository.ts` и `repositories/transcriptPostRepository.ts`
работают с БД, `bot/commands/transcriptPost.ts` общается с пользователем.

```
PDF (Telegram) → pdfParser → ClientTranscript
                                  ↓
                    transcriptProcessingService (2 поста × до 3 попыток)
                                  ↓
      transcriptPostGenerator → mainIdeaExtractor → embeddings
                                  ↓
        дедупликация против NataliaPost + TranscriptPost (порог 0.75)
                                  ↓
                          TranscriptPost → Telegram
```

Подробности — в [features/TRANSCRIPT_POST_GENERATION.md](features/TRANSCRIPT_POST_GENERATION.md).

# Назначение папок

## ai/

Работа с OpenAI.

Содержит генерацию идей, генерацию постов и анализ контента.

AI не знает, откуда пришли данные и куда они отправятся дальше.

---

## bot/

Telegram Bot.

Получает команды пользователя.

Отправляет идеи.

Получает выбор пользователя.

Показывает готовые посты.

Внутри нет бизнес-логики.

---

## parser/

Получение новых публикаций конкурентов.

Отвечает только за загрузку информации.

Не анализирует её.

---

## cron/

Все задачи, запускаемые по расписанию.

Например:

- анализ конкурентов;
- генерация идей;
- ежедневные проверки.

Cron только запускает сервисы.

---

## services/

Главный слой проекта.

Именно здесь собирается весь pipeline.

Например:

```
получить новые посты

↓

сохранить

↓

сгенерировать идеи

↓

сохранить

↓

отправить в Telegram
```

Практически вся бизнес-логика проекта находится именно здесь.

Внутри `services/` файлы группируются по доменным сущностям (подпапки),
а не лежат плоским списком:

```
services/
└── nataliaPost/
    ├── mainIdeaProcessor.ts
    ├── mainIdeaProcessor.types.ts
    └── mainIdea.config.ts
```

Так по названию папки сразу понятно, к какой сущности относится код;
при появлении новых доменов (`idea`, `competitorPost`) заводятся
соседние подпапки.

---


## repositories/

Единственная папка, которая работает с базой данных.

Никакой другой модуль не должен напрямую использовать Prisma.

Все операции проходят через repositories.

---

## db/

Инициализация подключения к базе данных.

Экспорт Prisma Client.

---

## prompts/

Markdown-файлы с инструкциями для OpenAI.

Здесь будут храниться:

- стиль Натальи;
- генерация идей;
- генерация постов;
- анализ конкурентов.

Промпты отделены от кода, чтобы их можно было изменять независимо.

---

## core/

Общая инфраструктура проекта.

### config/

Конфигурация приложения.

- env
- настройки
- zod validation

### lib/

Инициализация внешних клиентов.

Например:

- Prisma
- OpenAI
- Telegram Bot

---

## shared/

Общие вещи, которые могут использоваться где угодно.

Например:

- utils
- helper functions
- constants
- общие TypeScript типы

---

# Принципы разработки

При написании кода придерживаемся следующих правил.

## Один модуль — одна ответственность

Каждый модуль должен выполнять только одну задачу.

---

## Services управляют процессом

Вся бизнес-логика находится в services.

Остальные папки являются исполнителями.

---

## Repository Pattern

Весь доступ к базе данных осуществляется только через repositories.

Никаких вызовов Prisma напрямую из parser, ai или bot.

---

## Промпты отделены от кода

Все инструкции OpenAI находятся в папке `prompts`.

Код не содержит больших строковых промптов.

---

## Минимальная связанность

Модули должны зависеть друг от друга как можно меньше.

Например:

```
Bot

↓

Service

↓

Repository

↓

Database
```

а не

```
Bot

↓

Prisma

↓

OpenAI

↓

Parser
```
