# Data Architecture — SMM Agent

Этот документ фиксирует модель данных и поток работы MVP.

Всё, что связано с векторами и дедупликацией по смыслу (embeddings, similarity
search, pgvector), вынесено в отдельный документ: [`Embeddings.md`](./Embeddings.md).
Здесь описываются только сущности, их поля и жизненный цикл данных.

> **Принцип MVP:** фиксируем именно эту модель и больше пока ничего не добавляем.
> Всё остальное (аналитика, несколько идей на пост, поиск похожих постов как
> фича для пользователя и т.д.) можно добавить позже без переделки архитектуры.

---

# Сущности проекта

## Competitor

**Назначение**

Хранит информацию о Telegram-каналах конкурентов.

**Связана с**

* `CompetitorPost` (один канал → много постов)

**Основные данные**

* id
* name
* url
* isActive
* createdAt

---

## CompetitorPost

**Назначение**

Хранит оригинальные посты конкурентов.

Это основной источник информации для генерации идей.

Каждый новый пост проходит следующие этапы:

```
Получен
   ↓
Сохранён
   ↓
Из него создана идея
   ↓
Помечен как обработанный
```

**Связана с**

* Competitor
* Idea

**Основные данные**

* id
* competitorId
* telegramPostUrl
* text
* publishedAt
* isProcessed
* ideaId
* createdAt

---

## NataliaPost

**Назначение**

Хранит все посты Натальи.

Используется для проверки повторов — чтобы не генерировать идеи на уже раскрытые темы.

AI не использует эти посты как эталон стиля — стиль задаётся промптом.

Посты нужны только для дедупликации через векторный поиск.

**Связана с**

Ни с чем напрямую. Используется для дедупликации через embedding.

**Основные данные**

* id
* text
* mainIdea
* **embedding** — вектор от `mainIdea`, используется для проверки «не повторяем ли мы уже раскрытую тему». Подробнее — в [`Embeddings.md`](./Embeddings.md).
* publishedAt
* createdAt

---

## Idea

**Назначение**

Хранит идеи, созданные AI.

Каждая идея создаётся **из одного поста конкурента**.

Именно идеи отправляются пользователю в Telegram.

После выбора идеи на её основе создаётся полноценный пост.

**Связана с**

* CompetitorPost
* GeneratedPost

**Основные данные**

* id
* competitorPostId
* title
* thesis
* goal
* **embedding** — вектор от `title + thesis`. Считается сразу после генерации идеи и используется для дедупликации (см. этап 5 и [`Embeddings.md`](./Embeddings.md)).
* status (`NEW`, `SENT`, `SELECTED`, `REJECTED`, `DUPLICATE`)
* createdAt

---

## GeneratedPost

**Назначение**

Хранит готовый пост, который AI написал после выбора идеи.

Используется как черновик перед публикацией.

**Связана с**

* Idea

**Основные данные**

* id
* ideaId
* text
* createdAt

---

## GenerationRun

**Назначение**

Хранит информацию о каждом запуске генерации.

Используется не бизнес-логикой, а системой.

Позволяет понять:

* когда был последний запуск;
* успешно ли он завершился;
* сколько данных было обработано;
* сколько идей создано;
* **во сколько запросов/токенов обошёлся прогон** (для контроля стоимости при батчинге).

Следующий запуск ориентируется именно на него (берёт посты, опубликованные
после `finishedAt` последнего успешного прогона).

**Основные данные**

* id
* startedAt
* finishedAt
* processedPosts
* generatedIdeas
* acceptedIdeas
* rejectedIdeas *(отброшены как дубли)*
* openaiRequests *(сколько запросов ушло в OpenAI — для контроля расходов)*
* status (`RUNNING`, `SUCCESS`, `FAILED`)

# Поток работы системы

## 1. Запуск

Во вторник и четверг в 10:00 cron запускает новый прогон и создаёт запись
`GenerationRun` со статусом `RUNNING`.

↓

## 2. Поиск новых постов

Парсер получает список активных конкурентов (`isActive = true`).

Для каждого канала ищет посты, опубликованные **после `finishedAt` последнего
успешного прогона**.

↓

## 3. Сохранение

Все найденные посты сохраняются в `CompetitorPost` (`isProcessed = false`).

На этом этапе никакой AI ещё не используется.

↓

## 4. Генерация идей (батчами)

> **Ключевое решение по стоимости:** мы НЕ отправляем по одному запросу на
> каждый пост конкурента. Эталонные посты больше не используются, стиль задаётся
> промптом напрямую.

Новые посты разбиваются на **чанки по 15–20 постов**. Каждый чанк отправляется
в OpenAI **одним запросом**.

В запросе AI получает **один раз на весь чанк**:

* промпт со стилем Натальи;
* список новых постов конкурентов (15–20 штук).

AI возвращает **массив идей**, по одной на каждый пост, строго в том же порядке
(в ответе каждая идея явно ссылается на исходный пост — по индексу/id, чтобы не
потерять привязку). Формат ответа фиксируем через structured output / JSON schema.

Каждый элемент ответа:

* competitorPostId (для привязки)
* title
* thesis
* goal

↓

## 5. Проверка на повтор (дедупликация по вектору)

Для каждой сгенерированной идеи считается `embedding` (от `title + thesis`).

Затем через векторный поиск (pgvector, cosine similarity) ищутся ближайшие
записи среди:

* уже существующих `Idea.embedding`;
* `NataliaPost.embedding` (по `mainIdea`).

Логика решения (без обращения к LLM — чистая математика, очень дёшево):

* если similarity ближайшего соседа **выше порога** (стартовое значение ~0.85) —
  идея считается дублем: `status = DUPLICATE`, пользователю не показывается;
* иначе идея сохраняется как `NEW`, её embedding записывается в БД, и она
  участвует в дедупликации следующих идей этого же прогона.

Пост конкурента помечается как обработанный (`isProcessed = true`) и получает
`ideaId`.

Подробное объяснение векторов, порога и SQL-запроса — в [`Embeddings.md`](./Embeddings.md).

↓

## 6. Завершение прогона

Запись `GenerationRun` обновляется:

* время окончания (`finishedAt`);
* количество найденных постов;
* количество созданных идей;
* количество принятых идей;
* количество отброшенных как дубли;
* количество запросов в OpenAI;
* статус (`SUCCESS` / `FAILED`).

↓

## 7. Telegram

Пользователь получает список новых идей (`status = NEW`).

Каждая идея содержит:

* заголовок;
* тезис;
* цель;
* кнопку **«Сгенерировать пост»**.

После отправки идея переходит в `status = SENT`.

↓

## 8. Генерация поста

После выбора идеи (`status = SELECTED`) OpenAI получает:

* выбранную идею;
* оригинальный пост конкурента;
* промпт со стилем написания.

AI генерирует полноценный пост.

↓

## 9. Сохранение

Готовый текст сохраняется в `GeneratedPost` и отправляется пользователю в Telegram.

# Хранение данных (retention)

Прогоны идут 2 раза в неделю, база небольшая (~500 МБ), в старых данных смысла
нет. Поэтому политика хранения простая и агрессивная:

| Данные | Что делаем |
|--------|-----------|
| `CompetitorPost` | Обработанные посты (`isProcessed = true`) старше **30 дней** удаляются. Свежие держим на случай перегенерации идеи. |
| `Idea` со статусом `NEW`/`SENT` | Идеи, которые пользователь не выбрал, старше **14 дней** — удаляются. Их embedding уже сыграл роль в дедупликации своего прогона; долго держать незачем. |
| `Idea` со статусом `DUPLICATE` | Удаляются сразу по завершении прогона (нужны были только для логов, можно не хранить). |
| `Idea` со статусом `SELECTED` + `GeneratedPost` | Храним дольше (например 90 дней) — это фактически история контента. |
| `GenerationRun` | Держим последние **50 прогонов**, старые удаляем (нужен только последний успешный, остальное — для статистики). |
| `NataliaPost` | Не удаляем — это база знаний. |

> **Важно про дедупликацию и удаление.** Проблема «наслаивания» решается НЕ
> только удалением. Основной механизм — векторный поиск: рост числа записей не
> раздувает промпт, потому что мы ищем top-K похожих, а не суём весь список в
> запрос. Удаление здесь — только гигиена диска, а не способ контролировать
> размер промпта. Детали — в [`Embeddings.md`](./Embeddings.md).

Очистка выполняется отдельной фоновой задачей (cron), не смешанной с основным
прогоном генерации.

# Жизненный цикл данных

```text
Competitor
      │
      ▼
CompetitorPost ──── batch ───► OpenAI ──► Idea ──► (dedup по вектору)
      │                                     │
      │                                     ▼
      │                              GeneratedPost
      │
GenerationRun ─── управляет каждым циклом обработки

NataliaPost
      │
      ▼
Используется для дедупликации через embedding (проверка повторов тем)
```

# Что осознанно НЕ входит в MVP

* Несколько вариантов идеи на один пост конкурента.
* Несколько вариантов готового поста на одну идею.
* Поиск похожих постов как пользовательская фича (сейчас вектор — только для внутренней дедупликации).
* LLM-проверка «спорных» дублей (доверяемся порогу; можно добавить позже).
* Аналитика конкурентов и рекомендации по контент-плану.
