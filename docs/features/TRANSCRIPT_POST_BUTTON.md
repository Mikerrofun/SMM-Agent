# Кнопка «Найти ещё пост» — генерация дополнительных постов из транскрипции

---

**Дата:** 15.08.2026  
**Теги:** #features #transcript-post #telegram-bot #inline-keyboard

---

## 1. Зачем

Базовая команда `/transcript_post` генерирует 2 поста из транскрипции встречи. Но одна встреча может содержать больше инсайтов — если после первых двух постов пользователь хочет получить ещё один, раньше приходилось загружать PDF заново.

Кнопка **«Найти ещё пост»** позволяет продолжить генерацию из той же транскрипции сколько угодно раз — до тех пор, пока система находит уникальные темы.

---

## 2. Как работает

### Базовый флоу (без кнопки)

```
Юзер: /transcript_post
Бот:  📄 Отправь PDF файл...

Юзер: [meeting.pdf]
Бот:  ⏳ Генерирую посты...

Бот:  ✅ Пост 1
      [текст поста]

Бот:  ✅ Пост 2
      [текст поста]

Бот:  ✅ Готово! Сгенерировано 2 поста из транскрипции.
      [кнопка: 📝 Найти ещё пост]
```

### Флоу с кнопкой

```
Юзер: [клик «Найти ещё пост»]
      ↓
Бот снимает клавиатуру (защита от двойного клика)
      ↓
Бот:  ⏳ Ищу уникальную тему в транскрипции...
      ↓
Сервис: достаёт все SENT-посты транскрипции
        собирает их mainIdea → usedMainIdeas
        запускает цикл 3 попыток для одного поста
      ↓
Три исхода:

1. Уникальная тема найдена:
   Бот:  ✅ Пост 3
         [текст]
   Бот:  ✅ Найден ещё один пост из этой встречи!
         [кнопка: 📝 Найти ещё пост]  ← новая кнопка, цепочка продолжается

2. Все 3 попытки дали дубли:
   Бот:  💭 Больше уникальных тем в этой встрече не найдено.
         Все инсайты из транскрипции уже использованы.
         ← кнопка НЕ возвращается, это стоп-механизм

3. Ошибка (LLM, embedding, сеть):
   Бот:  ❌ Произошла ошибка: [текст]
         Попробуй ещё раз.
         [кнопка: 📝 Найти ещё пост]  ← кнопка возвращается
```

Цепочка бесконечная: после каждого успешного поста кнопка появляется снова. Единственный стоп — исчерпание уникальных тем.

## 4. Технические детали

### Формат `callback_data`

```
transcript_more:<transcriptId>
```

Пример: `transcript_more:clxyz123abc`

**Ограничение Telegram:** максимум 64 байта. Один cuid ≈ 25 символов, префикс 17 символов → всего ≈ 42 байта, влезает.

**Почему только `transcriptId`, а не `transcriptId + postNumber`:**  
Два id не влезут в 64 байта. Номер поста высчитывается из БД: `getSentPosts().length`.

### Защита от двойного клика

```typescript
// Сразу после answerCallbackQuery()
await ctx.editMessageReplyMarkup({ reply_markup: undefined });
```

Клавиатура снимается **до** начала генерации. Если пользователь кликнет дважды быстро — второй клик попадёт в сообщение уже без кнопки и ничего не сделает.

In-memory замок (типа `Map<transcriptId, boolean>`) не нужен — вся логика идемпотентна: повторный запуск генерации для того же транскрипта просто создаст ещё один пост, если темы есть.

### Построение `usedMainIdeas`

```typescript
const sentPosts = await getSentPosts(transcriptId);
const usedMainIdeas = sentPosts.map((p) => p.mainIdea);
```

В `usedMainIdeas` попадают **все** посты со статусом `SENT` — и базовые 2 поста, и все посты, созданные через кнопку ранее.

Эти темы передаются в промпт, чтобы LLM не предлагал уже раскрытые инсайты:

```markdown
УЖЕ РАСКРЫТЫЕ ТЕМЫ (не повторяй их, выбери другой инсайт):
- Цены и ценность
- Делегирование задач
```

Это не гарантия (LLM может проигнорировать), но значительно снижает вероятность дубля на уровне генерации.

### Цикл попыток

Для кнопки используется **та же функция** `generateSinglePost()`, что и для базовой команды — код цикла попыток не дублируется.

```typescript
async function generateSinglePost(
  transcript: { id: string; text: string },
  usedMainIdeas: string[],
  postIndex: number,
  stats: ProcessingStats,
  errors: string[]
): Promise<TranscriptPostData | null>
```

Функция делает до 3 попыток: генерация → mainIdea → embedding → дедупликация. Первая уникальная принимается (`status = SENT`), три дубля → `null`.

### Дедупликация

Ключевое изменение: `findSimilarPosts()` фильтрует по `status = SENT`:

```sql
SELECT id, (1 - (embedding <=> $1::vector)) AS similarity
FROM "TranscriptPost"
WHERE embedding IS NOT NULL
  AND status = 'SENT'
  AND (1 - (embedding <=> $1::vector)) >= $2
ORDER BY similarity DESC
```

Черновики (`REJECTED`) не участвуют в сравнении — они мусор прошлых попыток. В выборку попадают только реально отправленные посты.

**Следствие:** два уже отправленных поста этой встречи автоматически участвуют в сравнении для третьего. Дополнительная проверка «новый пост не похож на предыдущие посты этой встречи» не нужна — векторный поиск покрывает это из коробки.

### Отличие от базовой команды

| Аспект | Базовая команда | Кнопка |
|---|---|---|
| Постов за раз | 2 (цикл `POSTS_PER_TRANSCRIPT`) | 1 |
| `usedMainIdeas` | Накапливается внутри прогона | Строится из БД (`getSentPosts`) |
| Запись транскрипции | Создаётся из PDF | Уже существует, достаётся по id |
| Результат | `ProcessingResult` с массивом постов | Один пост или признак исчерпания |
| Лимит | Нет (можно грузить PDF сколько угодно) | Нет (можно жать кнопку сколько угодно) |

## 5. Устойчивость к ошибкам

### Старое сообщение

Если пользователь кликнет по кнопке из сообщения недельной давности — ничего страшного:

1. `transcriptId` достаётся из БД
2. `getSentPosts()` возвращает актуальное состояние
3. Генерация идёт с текущим набором `usedMainIdeas`

Худший случай: если за неделю все темы исчерпаны другими кликами, пользователь получит «больше тем не найдено».

### Параллельные клики

Если два человека одновременно кликнут по одной кнопке (например, в групповом чате):

1. Оба запроса увидят одинаковый набор `sentPosts`
2. Оба запустят генерацию с одинаковым `usedMainIdeas`
3. LLM с высокой вероятностью предложит разные темы (температура 0.7, разные вызовы)
4. Оба поста пройдут дедупликацию независимо
5. Результат: либо два разных поста, либо один уникальный и один дубль

Это приемлемо. Если нужна жёсткая сериализация — добавить `SELECT ... FOR UPDATE` на уровне транзакции, но пока не требуется.

### Удалённая транскрипция

```typescript
const transcript = await getTranscriptById(transcriptId);
if (!transcript) {
  return { success: false, reason: 'error', error: 'Транскрипция не найдена' };
}
```

Пользователь получит внятное сообщение об ошибке + кнопка вернётся.

## 6. Почему так, а не иначе

### Почему не лимит на количество постов из одной транскрипции?

Лимит требует хранить счётчик и проверять его при каждом клике. Дедупликация — естественный лимит: когда темы кончатся, система сама остановится. Плюс это честно: если встреча насыщенная, пользователь получит 5 постов, если скучная — 2.

### Почему кнопка не снимается совсем после первого клика?

Если снять кнопку навсегда после первого клика, пользователь не сможет получить 4-й, 5-й пост. Цепочка кнопок — это UX: каждый раз пользователь **осознанно** запрашивает ещё один пост, а не получает сразу 10 штук залпом.

### Почему `bestCandidate` убран?

Раньше при 3 дублях отдавался пост с минимальной similarity. Проблема: этот пост помечался `isDuplicate = true`, но записывался как `SENT` → участвовал в дедупликации будущих постов → ужесточал порог.

Кнопка заменяет этот fallback: если базовая команда не нашла уникальную тему с 3 попыток, пользователь может кликнуть кнопку и запустить ещё 3 попытки. Это честнее: либо тема уникальна, либо её нет.

### Почему статус `REJECTED` по умолчанию, а не `SENT`?

**Безопасность.** Если забыть проставить статус — недостающий пост лучше, чем мусор в дедупликации. Пост «поднимается» до `SENT` только после успешной проверки.

### Почему `rejectedDraftIds` больше не нужен?

Раньше он исключал черновики текущего прогона из векторного поиска. Теперь фильтр `status = SENT` на уровне SQL делает это автоматически: свежесозданный пост `REJECTED` → в выборку не попадает.

### Почему номер поста высчитывается из БД, а не передаётся в `callback_data`?

64-байтовое ограничение Telegram: два cuid не влезут. Плюс номер, переданный в кнопке, устареет после первого же клика — БД всегда актуальна.

## 7. Взаимодействие с дедупликацией

Новый пост проверяется против:

1. **Всех постов Натальи** (`NataliaPost.embedding`)
2. **Всех отправленных постов транскрипций** (`TranscriptPost` со `status = SENT`)

Порог общий: `SIMILARITY_THRESHOLD = 0.75` из `services/idea/deduplication.config.ts`.

**Важно:** посты этой встречи и посты других встреч смешаны в одной проверке. Если пользователь загрузил две транскрипции про делегирование, второй прогон найдёт дубль с первым автоматически — отдельная логика не нужна.

## 8. Логи

Каждый клик кнопки логируется:

```
[TranscriptProcessing] Generating additional post { transcriptId }
[TranscriptProcessing] Found sent posts { sentPostsCount, usedMainIdeas }
[TranscriptProcessing] Attempt { postIndex, attempt, similarity, isDuplicate, source }
[TranscriptProcessing] Additional post generated { transcriptId, postId, totalAttempts }
```

Или:

```
[TranscriptProcessing] No unique topics found { transcriptId, totalAttempts }
```

По логам видно: сколько попыток потребовалось, какие темы уже использованы, почему пост был отклонён (дубль с каким источником).

## 9. Будущие улучшения (не в MVP)

- **Счётчик постов в кнопке:** «Найти ещё пост (создано: 3)» — показывает, сколько уже получено
- **План тем от LLM:** на старте прогона спросить у модели «сколько независимых инсайтов в транскрипции», остановиться раньше исчерпания попыток
- **Регенерация поста:** кнопка «🔄 Другой вариант» под каждым постом (аналогично `regenerate_post` для идей)
- **Групповой чат:** ограничение на одновременные клики через `SELECT ... FOR UPDATE`

Пока всё это не нужно — базовая механика работает.

## Преимущества

- ✅ Неограниченная генерация из одной транскрипции — не нужно грузить PDF повторно
- ✅ Естественный стоп-механизм через дедупликацию — нет мусора, нет произвольных лимитов
- ✅ Устойчивость к старым сообщениям — состояние в БД, а не в памяти бота
- ✅ Защита от двойного клика — клавиатура снимается сразу
- ✅ Цепочка кнопок — UX прозрачен, пользователь контролирует процесс
- ✅ Переиспользование кода — цикл попыток не дублируется, один `generateSinglePost()` на оба флоу
- ✅ Отказ от `bestCandidate` — дедупликация не деградирует, база не загрязняется
- ✅ Честная дедупликация — черновики (`REJECTED`) не участвуют в сравнении, только реальный контент
